# Springfield After Hours Toolkit 0.1.0

**A cross-platform SHAR mod-development toolkit featuring source-backed Game.lua
definitions and six small utilities for cleaning, comparing, inspecting, and
preparing mod projects — no game installation required.**

The first release. Two developer-facing parts ship together because they solve
the two halves of the same day: writing mission scripts, and getting the folder
around them fit to hand to someone else.

| Part                                         | What it gives you                                                            |
| -------------------------------------------- | ---------------------------------------------------------------------------- |
| **1. Game.lua Definitions** (`sah lua-defs`) | Editor autocomplete and argument checking for the verified `Game.*` commands |
| **2. SHAR Pocket Tools** (`sah pocket`)      | Six filesystem utilities for preparing and comparing mod projects            |

Both are cross-platform (macOS, Windows, Linux), both run entirely offline, and
**neither requires the game or Lucas' Mod Launcher to be installed.**

## Part 1 — Game.lua Definitions

**Editor support for the verified `Game.*` commands.**

Donut Team's `Game.lua` builds its command table **at runtime** — `AddCommand`
installs a closure per command — so no editor can discover those functions by
reading source. Donut Team's own published Lua Language Server definitions cover
the Custom Files API (`Output`, `GetModPath`, …) and deliberately stop there.
This fills the other half.

```sh
sah lua-defs install ~/path/to/your-mod --with-official          # shows the plan
sah lua-defs install ~/path/to/your-mod --with-official --apply  # writes it
```

You get **351 completions**: 339 commands, their 10 `Not_` inverses, and
`Game.EndIf()` / `Game.Not()`, which Game.lua defines outside its command
tables. Hover docs carry each command's required scope and argument range, and
argument counts are genuinely checked — LuaLS's `missing-parameter` and
`redundant-parameter` are both on by default, and the generated signatures
encode both bounds.

**Everything is derived, nothing is transcribed.** `Game.meta.lua` is generated
mechanically from `data/registries/commands.yaml`, which is itself derived by
parsing the `DefaultCommands`, `ASFCommands` and `DebugTestCommands` tables in
upstream `Game.lua` at a pinned commit. The generated file's header names that
repository, commit and file hash. CI fails if either derivation drifts.

**Argument names and types are `argN: any`** — not a placeholder, a refusal.
No source this project has read documents them, so inventing plausible ones
would be exactly the failure this toolkit exists to prevent.

| Command                              | Does                                                          |
| ------------------------------------ | ------------------------------------------------------------- |
| `sah lua-defs generate`              | Regenerate `Game.meta.lua` from the command registry          |
| `sah lua-defs check`                 | Verify definitions against the registry and the pinned commit |
| `sah lua-defs install <mod-project>` | Set a mod project up to use them in an editor                 |

`install` plans before it writes, preserves unrelated editor settings, unions
rather than replaces `Lua.workspace.library`, and never retargets a
`Lua.runtime.version` an author already chose. With `--with-official` it fetches
Donut Team's definitions **into your mod project** from a pinned commit, verifies
each file against a recorded SHA-256, installs `LICENSE.md` alongside them, and
fails clearly when offline rather than installing a partial set. Those files are
never committed to this repository.

Full guide: [`docs/getting-started/lua-definitions.md`](../getting-started/lua-definitions.md).

## Part 2 — SHAR Pocket Tools

**Six filesystem utilities for preparing and comparing mod projects.**

Aimed at the part of modding that is not authoring: the folder you are about to
zip up, the two mods you are not sure play nicely together, the release you want
to diff against the last one, the path you need to paste into a
`CustomFiles.ini` with the backslashes doubled correctly.

| Command                                | Does                                                  |
| -------------------------------------- | ----------------------------------------------------- |
| `sah pocket case-check <dir>`          | Case collisions, and references whose casing is wrong |
| `sah pocket clean-export <src> [dest]` | Clean copy without macOS, editor and temp junk        |
| `sah pocket conflicts <dir...>`        | Paths supplied by more than one mod, with hashes      |
| `sah pocket manifest <dir>`            | Deterministic path + size + SHA-256 record            |
| `sah pocket diff <old> <new>`          | Added, removed, modified, renamed, case-only changes  |
| `sah pocket path <project> <file>`     | Windows / POSIX / INI / Lua path forms, with `--copy` |

Aliases: `sah pocket case`, `sah pocket clean`.

### Design commitments

- **Read-only by default.** Only `clean-export` writes, and its default is to
  write a _copy_. Deleting from the original needs `--in-place` **and** `--yes`,
  and every removal is re-verified against the junk list and the containment
  check at the moment it happens.
- **Deterministic.** Manifests and JSON output are byte-identical across runs
  and across platforms: no timestamps, POSIX paths, code-unit rather than locale
  sorting, and manifests exclude themselves.
- **Confined.** Symlinks are never followed. Containment is checked _before_
  existence, so a traversal is answered "outside the project" rather than "no
  such file". Nothing outside the folder you name is ever read.
- **Offline.** No network client exists in the package.
- **No shell injection surface.** The clipboard helper is the only subprocess;
  it runs with an argument array and `shell: false`, with the text passed over
  stdin — a path may legally contain quotes, backticks and `$(...)`.
- **Absolute paths stay out of shareable output.** Manifests record a folder's
  name, not its location; `sah pocket path` refuses to emit one at all.
- **Honest about scope.** File overlaps are _potential_ conflicts. Renames are
  _candidates_. Neither is presented as a verdict.

### Exit codes

`0` nothing found · `1` found something · `2` could not run · `70` internal
error. **Code 1 is a finding, not a failure** — `diff` returns it whenever two
releases differ, which is the normal case.

Full guide: [`docs/getting-started/pocket-tools.md`](../getting-started/pocket-tools.md).

## Installing

**No game installation required.** Not published to npm — build from source:

```sh
git clone https://github.com/22500107Zc/springfield-after-hours-toolkit.git
cd springfield-after-hours-toolkit
npm install
npm run build
npm link -w packages/cli     # optional; makes `sah` available as a command
```

Requires **Node.js 20 or newer**. That is the whole list of prerequisites: no
game, no Mod Launcher, no Windows, no network access to run any tool in this
release.

Without `npm link`, substitute `node packages/cli/dist/bin.js` for `sah`
throughout.

**One optional step.** `npm run upstream:fetch` downloads Donut Team's `Game.lua`
(MIT) from a pinned commit into the git-ignored `vendor/` directory. It is
needed only to re-derive the command registry or to build a mod that ships
`Game.lua`. Every command in this release works without it.

## Quick start

### Part 1 — set an editor up for `Game.*`

```sh
# Preview what would be written into your mod project
sah lua-defs install ~/mods/my-mod --with-official

# Apply it
sah lua-defs install ~/mods/my-mod --with-official --apply

# Confirm the shipped definitions still match the registry and the pinned commit
sah lua-defs check
```

Open the project in an editor with the Lua Language Server (`sumneko.lua`)
installed. Type `Game.` and you get 351 completions, with scope and argument
range in the hover text.

### Part 2 — prepare a mod folder for release

```sh
# Would this break for someone on Linux, or inside a zip?
sah pocket case-check ~/mods/my-mod

# Make a clean copy to zip — the original is not touched
sah pocket clean-export ~/mods/my-mod ~/Desktop/my-mod-release

# Record exactly what you are shipping
sah pocket manifest ~/Desktop/my-mod-release -o ~/Desktop/my-mod-release/manifest.json

# What changed since last time?
sah pocket diff ~/releases/v0 ~/Desktop/my-mod-release

# Does it collide with another mod?
sah pocket conflicts ~/mods/my-mod ~/mods/someone-elses-mod

# Get the path form you need, on the clipboard
sah pocket path ~/mods/my-mod Resources/scripts/m0i.lua --form ini --copy
```

Every command takes `--json` for scripting.

## What is tested, and what is not

This distinction is the most important thing in this document, so it gets its
own section rather than a footnote.

### Tested — file and editor behaviour

Verified by 416 automated tests on macOS, Windows and Linux, on Node 20 and 22:

- **Generated definitions parse as real Lua 5.3** — checked with an actual Lua
  parser, not a regex.
- **Definitions match the command registry** — every verified command present,
  nothing invented, arity and scope correct, artifact byte-identical to what the
  generator produces, upstream pin unchanged. Each of those five kinds of drift
  has a test that creates it on purpose.
- **`install` writes what it plans and nothing else** — preserves unrelated
  editor settings, refuses a malformed settings file without touching it,
  verifies every official file against its pinned hash, and refuses to install a
  partial set when offline.
- **Every pocket tool's file behaviour** — collisions, mis-cased references,
  false-positive resistance against ordinary prose, junk classification,
  clean-export leaving the original untouched, symlinks pointing inside and
  outside a project, path traversal refusal, identical vs differing conflicting
  files, manifest stability and self-exclusion, added/removed/modified/renamed/
  case-only changes, spaces and Unicode and apostrophes in paths, and exit codes.
- **Determinism** — manifests are asserted byte-identical across repeated runs
  on each CI platform separately.

### Not tested — anything the game does

**Nothing in this release has been run in _The Simpsons: Hit & Run_.** No one who
built it had a game installation, a Mod Launcher installation, or Windows as a
daily driver.

Concretely, this release makes **no verified claim** that:

- a mod built by this toolkit loads;
- a mission script generated by it can be completed;
- editor autocomplete passing means a script works — **it does not.** LuaLS
  checks names and argument counts. It cannot know where in an emitted script a
  call lands, and scope rules in the generated file are documentation only. The
  generated file says so in its own header.
- a folder that passes every pocket tool check is a working mod — it may be
  completely broken;
- two mods reported as overlapping actually conflict at runtime, or that two
  mods with no overlap are safe together. Load order and override behaviour are
  not documented in any source this project has read.

The tools inspect and prepare **files**. Ask them about files, and they answer
about files.

## Test results

```
npm run check → 10/10 pass
```

typecheck · lint · format · test · build · registry drift · lua definitions
current · minimal campaign builds · pocket tools smoke test · the Springfield
After Hours example still correctly _refusing_ to validate.

```
npm test → 416 tests across 22 files, all passing
```

Fixtures are synthetic throughout. No game, no Mod Launcher, no copyrighted
assets, no network — in the test suite or anywhere else.

Two host capabilities genuinely vary and are **probed, not assumed**:

- **Case sensitivity.** macOS and Windows will not let `A.txt` and `a.txt`
  coexist, so a collision fixture cannot be created there. The collision logic is
  therefore tested against in-memory path lists on every platform, and
  _additionally_ against real colliding files where the filesystem allows it.
- **Symlink creation.** Windows refuses it without developer mode, so those
  tests skip on a host that cannot create links and run everywhere else.

No test was skipped or weakened to make CI pass.

## Limitations

**Both parts**

- Nothing here has been run in the game. See
  [What is tested, and what is not](#what-is-tested-and-what-is-not).
- Not published to npm, and not a VS Code Marketplace extension. Build from
  source.

**Game.lua Definitions**

- Argument names and types are `argN: any`, because no source read by this
  project documents them.
- Scope rules in the generated file are documentation only. `sah validate` does
  enforce scope; a language server cannot.
- `--with-official` needs network access at install time, and fails clearly
  rather than installing an incomplete set.

**Pocket Tools**

- "Potential conflicts" are potential. Overlap is a thing to look at, not a
  verdict.
- Rename detection is inference from identical hashes, not a recorded move. Two
  empty files are byte-identical and unrelated.
- The reference scanner reports mis-_casing_ only. It will not tell you a
  referenced file is missing entirely — that is a different problem, and it
  refuses to guess about it.
- The junk list is closed and will miss junk from a tool nobody has added yet.
  That is the intended trade against deleting someone's work.
- Symlink recreation during export may fail on Windows without developer mode.
  Reported, not silently ignored.
- Nothing has been exercised against a real published mod by its author.

**The wider toolkit, unchanged by this release**

- The locations and vehicles registries are still **empty** — not placeholders,
  empty, because no source consulted so far states any of it.
- Only the `dummy` objective compiles. Most objective pages upstream read
  "TODO", so their parameters are unknown and the toolkit refuses to guess.
- `sah ai` commands refuse to run; the diff-and-confirm review step is
  unimplemented.
- No plugin loader. The contract is typed; running third-party code safely is
  not solved.

## AI-assisted development disclosure

**This release was implemented with AI assistance.** The code, tests and
documentation were written by Claude (Anthropic) working in this repository,
with the design constraints, review and acceptance decisions coming from the
repository's maintainer.

That is stated plainly because it is relevant to how you should evaluate it: the
tests, the pinned hashes and the CI results are the things to trust, not the
provenance of the code. Every one of them is reproducible with `npm run check`.

It also shaped what is _in_ the release. Nobody working on this owns the game,
so both parts were deliberately chosen to be things that can be built and
verified honestly without it — one derives its content mechanically from a
pinned upstream file, the other operates on files and hashes. Where a claim
could not be checked, the tools refuse to make it: unresolved references are
build errors, undocumented argument types stay `any`, and overlapping paths are
called potential conflicts.
